# Порядок актуализации документации

**Обозначение:** UEBA-RS.АД.01

**Основание:** разделы 2.1–2.3 и глава 4 учебного пособия.

## 1. Общие положения

Документация считается частью программного продукта: изменение функциональности системы не может быть принято без проверки и, при необходимости, обновления соответствующих документов. Документы хранятся в формате Markdown в репозитории Git вместе с исходным кодом или в отдельном репозитории документации, а их версии фиксируются в файле CHANGELOG.md по схеме Major.Minor.Patch.

## 2. События, требующие обновления документов

Таблица – Изменения системы и затрагиваемые документы

| Изменение системы | Затрагиваемые документы | Тип версии |
|---|---|---|
| Новый экран, кнопка или функция дашборда | Руководство оператора | Minor |
| Изменение формулы расчёта, порогов или структуры данных | Все документы комплекта | Major |
| Новый параметр файла .env, новая служба, изменение установки | Руководство администратора | Minor |
| Новая таблица или поле базы данных | Описание базы данных, описание архитектуры | Minor |
| Новый компонент или внешняя интеграция | Описание архитектуры, руководство администратора | Minor |
| Новое сообщение об ошибке | Руководства оператора и администратора | Patch |
| Исправление опечатки, уточнение формулировки, правка примера | Соответствующий документ | Patch |

## 3. Периодичность пересмотра

Таблица – Периодичность пересмотра и ответственные

| Вид пересмотра | Периодичность | Ответственный | Результат |
|---|---|---|---|
| Внеплановый (при изменении функциональности) | В рамках каждой задачи на изменение, до слияния кода | Разработчик, внёсший изменение | Обновлённые документы в том же запросе на слияние |
| Плановый | Ежеквартально | Ответственный за документацию (разработчик) | Проверка всех документов на соответствие системе |
| Проверка руководства оператора | После каждого выпуска и не реже одного раза в полгода | Ведущий SOC-аналитик | Подтверждение, что описанные действия выполнимы |
| Проверка руководства администратора | После каждого выпуска и не реже одного раза в полгода | Системный администратор ИБ | Проверка команд установки и восстановления на тестовом стенде |
| Полный аудит | Ежегодно | Руководитель проекта | Решение о выпуске новой основной версии |

## 4. Ответственные лица

Таблица – Роли в процессе актуализации

| Роль | Обязанности |
|---|---|
| Разработчик (автор изменения) | Обновляет документы одновременно с кодом, пишет запись в CHANGELOG.md |
| Ответственный за документацию | Следит за расписанием пересмотров, проверяет оформление и терминологию |
| Рецензент (ведущий SOC-аналитик или системный администратор ИБ) | Проверяет достоверность и применимость описанных действий |
| Руководитель проекта | Утверждает выпуск новой версии документации |

## 5. Процесс обновления

1. Разработчик создаёт ветку для изменения (например, docs/operator-new-export).
2. Вносит правки в файлы Markdown и добавляет запись в раздел «Не выпущено» файла CHANGELOG.md.
3. Фиксирует изменения коммитом с понятным сообщением (что и зачем изменено).
4. Создаёт запрос на слияние; рецензент проверяет содержание и оформление.
5. После одобрения изменения вливаются в основную ветку.
6. Ответственный за документацию определяет номер версии, переносит запись из раздела «Не выпущено» в новый раздел с датой и ставит тег версии.
7. Актуальные версии публикуются в общем хранилище документации, устаревшие остаются доступными через историю Git.

## 6. Версионирование

Таблица – Правила присвоения номера версии

| Часть номера | Когда увеличивается | Пример |
|---|---|---|
| Major (основная) | Изменена структура комплекта или смысл системы: новая формула, смена архитектуры, несовместимые изменения | 1.4.2 → 2.0.0 |
| Minor (второстепенная) | Добавлен новый раздел, документ, функция или параметр без нарушения прежнего описания | 1.4.2 → 1.5.0 |
| Patch (исправляющая) | Исправлены ошибки, опечатки, уточнены формулировки | 1.4.2 → 1.4.3 |

## 7. Контроль актуальности

- в шаблон запроса на слияние добавлен пункт «Затрагивает ли изменение документацию?»;
- задача не считается выполненной, пока документы не обновлены (критерий готовности);
- в каждом документе указано обозначение, а в CHANGELOG.md — дата и описание каждой версии;
- при плановом пересмотре проверяются ссылки, примеры команд и соответствие скриншотов и диаграмм текущей версии системы;
- исходный текст диаграмм (PlantUML) хранится рядом с документами, что позволяет обновлять их так же, как текст.
